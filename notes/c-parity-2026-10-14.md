# C-parity findings: reliable.rs against the C reference

Date: 2026-10-14. Card: rs-reliable-port-matches-the-c-reference.w1.
Base: `d2d72081f52e2f915f4ea8fce465fdc8846de4dc` (sprint/reliable-rs-port), release 1.4.5.

The Rust port is compared against the C reference. The C reference that is reachable
from this job is the vendored copy in `wire-compat/c/`, pinned at 1.4.5 (commit
`e4e70927d1656ffcd822309fc2aa7af004c58f6a`). JOB.md names no C checkout and
`RELIABLE_C_DIR` is unset, so the C tree holding the audit fixes (branch
`sprint/reliable-audit-fixes` at or after `7862477e`) could not be read. Findings that
depend on a fix landed after the 1.4.5 tag are therefore marked QUESTION with what would
settle them. C is normative; STANDARD.md is the 1.4.x copy and is used only where the
vendored C does not spell a rule out.

Line references: `port` is a path in this repo; `c` is a path under `wire-compat/c/` in
this repo (the vendored 1.4.5 tree).

Verdict vocabulary: MATCH (compared, agrees), BUG (port wrong, fix proposed), DIVERGENCE
(behaviour differs, allowed, reason given), QUESTION (cannot decide without the fixed C).

## 1. Wire format — MATCH

Compared the packet header writer and reader, the fragment header reader, and the
constants.

- Packet header writer: `src/packet.rs:24` against `c/reliable.c:833` (the body from
  `reliable_write_packet_header`). Prefix bit 0 is 0 for a regular packet, bits 1-4 are
  set exactly when the corresponding ack_bits byte is not `0xFF`, and bit 5 is set when
  `(sequence - ack) mod 65536 <= 255`. The port computes the difference with
  `wrapping_sub` (`src/packet.rs:45`); C computes `sequence - ack` in `int` and adds
  65536 when negative (`c/reliable.c:857-860`). Same value, same comparison, same bytes.
- Packet header reader: `src/packet.rs:88` against `c/reliable.c:909`. Same length gates
  (3 bytes minimum, +1 for a one-byte ack, +2 for a two-byte ack, +1 per present
  ack_bits byte) and the same `0xFF` substitution for absent ack_bits bytes.
- Fragment header reader: `src/packet.rs:161` against `c/reliable.c`'s
  `reliable_read_fragment_header`. Prefix byte must be exactly 1, sequence little-endian,
  fragment id 0-based, `num_fragments` stored minus one, checks `num_fragments <=
  max_fragments` before `fragment_id < num_fragments`, non-last fragments exactly
  `fragment_size`, last `0..=fragment_size`, fragment 0 carries and re-encodes the
  canonical packet header and its sequence must equal the fragment sequence.
- Constants: `RELIABLE_MAX_PACKET_HEADER_BYTES 9` and `RELIABLE_FRAGMENT_HEADER_BYTES 5`
  — `src/lib.rs:96,99` against `c/reliable.h:87,88`. Match.

## 2. Sequence buffer — MATCH

`src/sequence_buffer.rs` against `c/reliable.c:179-408`.

- Stale test `can_insert`: `port:63` vs `c/reliable.c:305` — `!sequence_less_than(
  sequence, sequence - num_entries)`. Same.
- Insert: `port:73` vs `c/reliable.c:302` — stale check first, then advance when
  `sequence + 1 > sequence`. Same ordering.
- `insert_advance_first`: `port:95` vs `c/reliable.c:329`
  (`reliable_sequence_buffer_insert_with_cleanup`) — advance check first, stale check in
  the `else`; reassembly uses this variant. Same.
- Advance: `port:113` vs `c/reliable.c:318`. Same.
- `remove_entries`: `port:42` vs `c/reliable.c:259`. `finish < start` adds 65536; if the
  span is shorter than the buffer, clear `start..=finish` modulo; otherwise clear every
  slot. Same. The port carries the empty marker as `None` in `entry_sequence` where C
  uses `0xFFFFFFFF` (`port:9` comment; C `c/reliable.c:368,395`); the four-bytes-per-slot
  shape and every observable result are identical.
- `exists`/`find`: `port:128,132` vs `c/reliable.c:381,387`. Same.
- `generate_ack_bits`: `port:152` vs `c/reliable.c:400` — `ack = sequence - 1`, bit `i`
  set when `ack - i` exists, 32 bits. Same.

## 3. Receive path ordering and counters — MATCH

`src/endpoint.rs:488` (`receive_packet_internal`) against `c/reliable.c:1250`.

- Regular packet: increment `num_packets_received`, read header (invalid -> 
  `num_packets_invalid`), receive-length gate (`num_packets_too_large_to_receive`), stale
  (`num_packets_stale`), duplicate (`num_packets_duplicate`), then process; only on
  `process == true` insert the received entry and walk the ack bits. Order matches
  `c/reliable.c:1265-1380`.
- Fragment: read header (invalid -> `num_fragments_invalid`), reject if the sequence is
  already in `received_packets` (no counter, as C), insert into reassembly, count
  mismatch -> `num_fragments_invalid`, duplicate fragment -> no counter, store, complete
  -> recursive `receive_packet_internal`, then `num_fragments_received`. Matches
  `c/reliable.c:1370-1490`.
- The eleven counters, order and names: `src/endpoint.rs:72-96` against
  `c/reliable.h:74-84` and `c/reliable.h:269`. Same eleven, same order.

## 4. Replay and window semantics — MATCH against vendored 1.4.5 / QUESTION against the fix

- A regular packet moves the received window only through `received_packets.insert`
  after `process` returns true: `port:574-581`, C `c/reliable.c:1315-1325`. Same.
- A first fragment advances the received window via
  `self.received_packets.advance(fragment_header.sequence)` at `port:667`, matching
  `reliable_sequence_buffer_advance( endpoint->received_packets, sequence )` at
  `c/reliable.c:1423`. The vendored trees agree.
- QUESTION: checklist item 4 states the *fixed* C "moves it only when a packet is
  accepted; a fragment never moves it", and item 9 names this as a C follow-up
  (`fragment_reassembly still advances its own window on a first fragment`, letting a
  far-ahead unfinished fragment stale a genuine fragmented packet). The vendored 1.4.5
  still advances (C line 1423) and so does the port (port line 667), so the two agree
  today. Whether they agree with the fixed C cannot be checked here: no C tree holding
  the fix is reachable (`RELIABLE_C_DIR` unset). A card would re-run the differential
  test once the fixed C is vendored, and remove the `advance` call on both sides if the
  fix dropped it.

## 5. Malformed input — MATCH (with a QUESTION on zero-length)

Oversize, truncated headers and bad fragment counts are counted and ignored; none panics,
throws or reads out of bounds. Zero-length is the exception: both implementations abort on
it (see below), which is why the differential transcript omits it.

- Zero-length receive: both reject before the first byte. Port `assert!(!packet_data
  .is_empty())` at `src/endpoint.rs:493`; C `reliable_assert( packet_bytes > 0 )` at
  `c/reliable.c:1252`. The two guards are gated differently: the port's `assert!` is
  active in every build, so a zero-length receive always panics; the C `reliable_assert`
  is gated on `RELIABLE_DEBUG` (`c/reliable.h:289-300`), defined by
  `wire-compat/build.rs:7`, so it traps in the wire-compat build but is a no-op in a
  production C build, where `packet_data[0]` at `c/reliable.c:1262` reads out of bounds.
  In the builds the differential test exercises the two agree (both abort). MATCH against
  the vendored 1.4.5; QUESTION against the checklist's wording: neither implementation
  "counts and ignores" a zero-length receive, so "never a panic, throw, trap" is not what
  the 1.4.5 C does. Settle against the fixed C, which may have turned this into a
  counted-and-ignored path.
- Oversize receive: port gate `packet_bytes > max_packet_size + 9 + 5` at
  `src/endpoint.rs:497`; C gate `(int64_t)packet_bytes > max_packet_size + 9 + 5` at
  `c/reliable.c:1254`. Both increment `num_packets_too_large_to_receive` and return.
  Same.
- Truncated packet header: `src/packet.rs:91,107,115,125` vs `c/reliable.c:909` — the
  same minimum-length gates in the same order; invalid -> `num_packets_invalid`.
- Bad fragment counts (`num_fragments > max_fragments`, `fragment_id >= num_fragments`,
  count mismatch, duplicate): `src/packet.rs:184,191`, `src/endpoint.rs:675,686`
  against `c/reliable.c` `reliable_read_fragment_header` and `1417,1439`; each increments
  `num_fragments_invalid` (or nothing, for a duplicate) exactly as C.

## 6. Config validation and defaults — DIVERGENCE (allowed)

Defaults: `src/endpoint.rs:48-67` against `c/reliable.c:522-545`. Every default matches:
16 KiB max packet, fragment_above 1024, 16 fragments of 1024, ack buffer 256, sent and
received 256, reassembly 64, rtt smoothing 0.0025, rtt history 512, loss 0.1, bandwidth
0.1, header 28. MATCH.

Refusals: `Endpoint::new` (`src/endpoint.rs:267-318`) panics where
`reliable_config_valid` (`c/reliable.c:553-620`) logs and returns 0 so
`reliable_endpoint_create` returns NULL. The port checks the same conditions in the same
effective set: positive sizes; `max_fragments` 1..=256; `fragment_above <=
max_packet_size`; fragment capacity covers the max packet by the same division
(`port:275` vs `c/reliable.c:605`); fragment product against a packet-length bound
(`port:282-289` vs `c/reliable.c:615`); `packet_header_size + max_packet_size` against a
packet-length bound (`port:303-309` vs `c/reliable.c:638-644`). C also refuses a NULL
config and a NULL transmit/process callback (`c/reliable.c:557,588`); neither is
representable in the Rust API (config is by value, callbacks are closures), so there is
nothing to refuse.

DIVERGENCE (allowed, documented in CLAUDE.md and CHANGELOG.md): config errors are panics
in the port and a NULL return in C. The Rust API is deliberately `Endpoint::new -> Self`,
no `Result`. A caller of an invalid config observes a panic instead of NULL.

DIVERGENCE (allowed, documented in CHANGELOG.md lines 78-88): the two packet-length
bounds are `u32::MAX` in the port (`src/endpoint.rs:287,307,316`) and `INT_MAX` in C
(`c/reliable.c:615,644`). C's bound is the width of its `int`; the port stores the length
in a `u32` only for the bandwidth counters. A configuration with a sum in `[2^31, 2^32]`
is refused by C and accepted by the port. Nothing on the wire depends on it. Proposed
card: none — this is the recorded intent.

QUESTION: `packet_header_size` negative. C refuses it (`c/reliable.c:633`); the port's
field is `usize` and cannot be negative. The port documents this at
`src/endpoint.rs:300-302` and relies on a cast of a negative int landing on a huge value
that the sum check refuses. That is a correct refusal but by the other check, so the
error message differs from C's. Minor; a card could add an explicit `packet_header_size`
bound if the API ever exposes a signed type.

## 7. Statistics — DIVERGENCE (allowed)

- rtt min/max/avg empty state decided by a count, not a sentinel: `src/endpoint.rs:804-834`
  (`min_rtt = f32::MAX`, `count`) against `c/reliable.c:1587-1618` (`FLT_MAX`, `count`).
  Match.
- Jitter avg/max vs min rtt: `src/endpoint.rs:837-853` vs `c/reliable.c:1622-1660`.
  Match.
- Packet loss: `src/endpoint.rs:876-902` vs `c/reliable.c:1682+`. The base sequence is
  the same value: C writes `(sequence - buffer_size + 1) + 0xFFFF`
  (`c/reliable.c:1683`), which is `sequence - buffer_size` mod 65536; the port writes
  `sequence().wrapping_sub(buffer_size)` (`src/endpoint.rs:878`). Match.
- Bandwidth: `smoothed_bandwidth_kbps` at `src/endpoint.rs:186` vs C's per-statistic
  loops. Same sample window (`num_entries / 2`), same `kbps = bytes / dt * 8 / 1000`,
  same `0.00001` dead zone. Match.
- `Reset` clears every statistic and refills rtt history with -1:
  `src/endpoint.rs:771-796` against C `reliable_endpoint_reset`. Match.
- DIVERGENCE (allowed, stats-only, never on the wire): stddev jitter squares. The port
  computes `(sum / count as f32).sqrt()` at `src/endpoint.rs:867`; C computes
  `(float) pow( sum / (float)count, 0.5f )` at `c/reliable.c:1679`. `sqrtf` and
  `pow(x, 0.5)` are not required to agree in the last ulp. Both round to `f32`; the
  port keeps the tighter `sqrt`. Nothing on the wire carries this value.
- DIVERGENCE (allowed, stats-only): C's build switched to `-ffp-contract=off`
  (CHANGELOG.md lines 92-96) so its float statistics do not fuse multiply-add across
  architectures. `wire-compat/build.rs` does not pass `-ffp-contract=off` to the C
  compiler, so the wire-compat C build may contract by the host default while the Rust
  build does not fuse at all. No float reaches the wire, so this cannot affect the
  cross-feed or transcript tests on the exercised inputs; it could move a C statistic by
  an ulp. Proposed card: add `-ffp-contract=off` (and `/fp:precise` on MSVC) to the
  wire-compat build so the two sides' statistics are compared on equal flags.
- Backwards-clock negative-rtt guard: the port's `debug_assert!( rtt >= 0.0 )` at
  `src/endpoint.rs:598` is debug-gated; C's `reliable_assert( rtt >= 0.0 )` at
  `c/reliable.c:1349` is gated on `RELIABLE_DEBUG`. Both are off in their release builds,
  so a backwards clock stores a negative rtt silently on both sides. MATCH — the known
  candidate "debug_assert! where C asserts at runtime" is refuted: C's check is equally
  build-gated, not a runtime assert.

## 8. Memory — DIVERGENCE (allowed) / MATCH

- Reassembly buffer zeroed: the port allocates with `vec![0; packet_buffer_size]` at
  `src/endpoint.rs:665`; vendored C zeroes with `memset( ..., 0, packet_buffer_size )` at
  `c/reliable.c:1452`. Match. (C 1.4.5's guarantee; the port's allocation is
  zero-initialised by construction, CHANGELOG.md lines 141-145.)
- Reassembly buffer slack: C allocates `MAX_PACKET_HEADER_BYTES + num_fragments *
  fragment_size + 8` (`c/reliable.c:1434`) — 8 bytes of slack past the largest packet the
  fragments can build. The port allocates exactly `MAX_PACKET_HEADER_BYTES +
  num_fragments * fragment_size` (`src/endpoint.rs:661-662`) and instead guards a
  would-overrun store with `end_offset > self.packet_data.len()` at `src/endpoint.rs:172`.
  DIVERGENCE (allowed): the 8 bytes are never read or written and neither size is
  observable from outside the endpoint; the port's explicit guard is the stronger
  property. This is the "no +8 slack" candidate from the card, confirmed.
- Config name: C forces a NUL onto its copy and logs the caller's name with `%.*s`
  (`c/reliable.c:548-551`, `RELIABLE_MAX_NAME_CHARS`); the port's `Config::name` is a
  `String`, length-delimited, and every log prints it whole. No terminator to run off.
  Match by construction (CHANGELOG.md lines 147-152). PROVIDED.
- Allocation failure refused and counted: C guards the reassembly allocation and
  increments `NUM_FRAGMENTS_INVALID` on NULL (`c/reliable.c:1440-1449`); Rust's
  `vec![0; n]` aborts rather than returning NULL to safe code, so there is no null branch
  and no counter to increment. DIVERGENCE (allowed, CHANGELOG.md lines 133-139).
- Unfinished-reassembly byte budget C is adding: not present in the vendored 1.4.5 and
  not in the port. QUESTION: the checklist names it as a C fix landing after 1.4.5, so it
  cannot be compared here. A card would read the fixed C and port the budget.

## 9. The C follow-ups the C fix reports named — MATCH against 1.4.5 / QUESTION against the fix

`src/endpoint.rs:667` advances `received_packets` on a first fragment, matching
`c/reliable.c:1423`. The checklist names this as something the C fix reports call out (a
far-ahead unfinished fragment can stale a genuine fragmented packet), so the fix may have
removed or narrowed it. The reachable (1.4.5) C still has it and the port matches it.
QUESTION: the fixed C is not reachable (`RELIABLE_C_DIR` unset). A card would re-run the
differential test against the fixed C and change the port only if the fixed C changed.
